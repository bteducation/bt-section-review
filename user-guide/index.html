YOUR WEBSITE, IN YOUR HANDS

Website user guideBT Education

A practical handbook for everyday content updates, confident publishing and website administration.

Version 1.0 · 13 November 2026 · Prepared by Focusin Studio

    Start here

    This guide explains how to maintain the rebuilt BT Education website: edit content, create pages, manage English and Chinese versions, and understand the settings that keep the site running.

    For everyday editing, use Sanity. You do not need GitHub, Vercel or a developer to change content within the existing page sections. New layouts, form behaviour, URL redirects and service configuration belong with the website administrator.

    Your website tools

    Tool What you use it for
    BT Education CMS Sign in to Sanity to edit and publish website content. Use your invited account.
    Rebuild review website Check the rebuilt website, including the English and Chinese pages.
    Section review site View the earlier section concepts. These are design mockups, not the live CMS.
    Vercel dashboard Administrator access for deployments, domains and environment variables.
    Sanity project management Administrator access for members, datasets, API access and webhooks.

    Which website should I check? The project’s 11 November 2026 release record identifies the Vercel address above as the rebuilt website and says that bteducation.com.au still served WordPress at that time. Confirm the current launch status with Focusin Studio before treating the custom domain as the rebuild. This guide does not confirm a domain cutover.

    A normal update

    1. Open the correct document and language in Sanity.
    2. Edit the content and wait for the draft to finish saving.
    3. Review the page in draft preview when needed.
    4. Resolve validation errors and obtain any required content approval.
    5. Click Publish, then check the public page and its links.

    Saving a draft, marking content as approved, publishing content and deploying website code are four different actions.

    Find the right document

    The Studio is titled BT Education CMS. Its navigation starts with shared settings, followed by page collections. The same subject document can appear in both a category collection and the general Subject Page list; these are views of the same content.

    Studio area What it controls
    Home Page Homepage content and section order. Edit the existing English or Chinese document.
    Standard Page General pages such as About, Results, Pricing, Contact and campaign pages.
    Subject Page Subject and program content, nested subject URLs and course-finder availability.
    Primary School Pages, Secondary School Pages, VCE Subject Pages, IB Pages, UCAT Pages Filtered subject lists based on the URL handle.
    Campus Page Individual campus pages and their sections.
    Blog Post An individual article.
    Blog Index Blog landing-page wording, featured article, pagination and final CTA.
    Site Settings, Header Settings, Footer Settings Shared content used across the website.
    Welcome Quiz Settings Bilingual quiz wording, options and availability.
    Subject page bottom sections Shared sections inherited by subject pages in each language.

    Check the document’s Locale and URL before editing. Search by the title or handle if a page is not in the category you expected. A subject with a short standalone handle may only appear in the general Subject Page list.

    Edit the existing settings documents. Do not create extra copies of Site, Header, Footer or Welcome Quiz Settings. Home Page and Blog Index should also have only the intended document for each language.

    Edit an existing page

    1. Open the page collection, then select the correct title and Locale.
    2. Expand Sections (or Homepage sections) and open the section you want to change.
    3. Update the visible heading, text, image, button or item. A document’s internal title is not always the heading visitors see; the hero has its own heading field.
    4. Use the drag handle to reorder a whole section. Reorder cards, FAQ items or table rows inside their own list when that is the intended change.
    5. Check links, media descriptions and both desktop and mobile presentation.
    6. Publish the document when ready. Repeat for the other language if the change applies to both.

    Example: update a paragraph. Open the page → Sections → Rich text → edit the body → check any links → preview → Publish.

    Example: change a button. Open its section → the relevant CTA → edit Label and Path or URL. Use Open link for a normal destination, or Open welcome quiz for the quiz. Keep a valid destination even for a quiz button: it is the fallback when the quiz is disabled.

    On Standard and Campus pages, Content review status and Review notes help track approval. Selecting Approved does not publish a page. Other page types may not expose these fields.

    Create a new page

    Use an existing supported page type. Sanity’s section selector shows which layouts that type supports; new custom sections require development.

    Create a general information page

    1. Open Standard Page and choose the new-document action.
    2. Enter Title and select Locale.
    3. Enter a stable Translation key, such as holiday-program-overview. Use that same key only for this page’s English/Chinese pair.
    4. Set Slug, for example holiday-program-overview. Review generated slugs rather than accepting them blindly.
    5. Complete Content review status, any review notes, and the SEO fields.
    6. Add at least one section. A useful starting order is Hero → Rich text → FAQs → Call to action; include only sections the page needs.
    7. Create the other language version if required. Translate its text, media descriptions and SEO fields.
    8. Ask for draft preview access, check both versions, resolve validation errors and publish when approved.
    9. Add a menu or page link where visitors should discover it. Publishing does not automatically add a page to the navigation.

    The example handle would produce /holiday-program-overview in English and /zh/holiday-program-overview in Chinese if both versions use that handle. These are examples, not existing pages.

    URL rules

    • Enter the page path without the domain or a leading/trailing slash. Do not put /en or /zh in the stored slug; the website adds language routing.
    • Use lowercase words and hyphens. For subject hierarchies, separate levels with /, such as primary-school-tutoring/year-5/english-tutoring.
    • Do not reuse a path already owned by another page in the same language. Avoid system routes such as api, search and blog; ask the developer if unsure.
    • Changing a published slug can break bookmarks, menus and search results. Coordinate the replacement links and redirect before changing it.
    • When duplicating a page, review its locale, translation key, slug, media, course availability and shared-section exclusions. Do not publish a duplicate with the original identifiers.

    Create a subject and configure the course finder

    1. Create a Subject Page and enter Subject name, Locale and a stable Translation key.
    2. Enter the complete URL handle, preserving the agreed hierarchy.
    3. Add SEO content and the required sections. Source Google Doc is a reference link only; the website does not automatically import edits from that document.
    4. For the standard content layout, use a light-teal hero, a white description, light-teal FAQs and white related-page content.
    5. If the hero supports it, enable Use global founder portrait. Edit Banner tagline heading and Banner message using approved wording. The portrait itself is managed once in Site Settings.
    6. In the description’s Rich text section, use the split layout when a text-and-media composition is needed. Upload the subject’s image or video into its own media field.
    7. Decide whether the page belongs in the course finder, then review its inherited bottom sections.
    8. Create and review the paired language page, publish both when approved, and test the actual finder combinations.

    Make a subject selectable

    Open Show in course finder and Course finder availability on the Subject Page.

    • Turn on Show in course finder.
    • Add a Course offering with Programs, Year levels and Available locations.
    • Use one row only when every selected combination genuinely shares that availability.
    • Add separate rows where availability differs. For example, if one year is offered only at Box Hill and another only at Glen Waverley, combining both years and campuses in one row would advertise extra combinations.
    • Update the corresponding English and Chinese documents, then publish them.

    The selected program, year and location must match the same offering row. A published page with no offerings will not appear in the finder. Overview/resource pages can remain published with the finder disabled. The homepage finder’s labels and messages are edited in its section; subject availability comes from the Subject Page documents.

    Manage English and Chinese

    English pages use unprefixed public routes, such as /pricing. Chinese pages use /zh/pricing.

    Pages and posts use separate language documents. Their Translation key connects the pair; the website does not translate content automatically. Keep the same document type and translation key for both languages. Their slugs may differ.

    1. Find or create the matching document with the other Locale.
    2. Check that its translation key exactly matches the original.
    3. Translate headings, paragraphs, buttons, SEO content and image/video descriptions.
    4. Check the destination of every link in the other language, including inline links.
    5. Publish each document separately and test the language switch from that specific page.

    Home Page uses the fixed key home; Blog Index uses blog. Do not create additional documents to change these keys.

    Site, Header, Footer and Welcome Quiz Settings contain English and Chinese fields together. Subject page bottom sections has separate English and 中文 entries. Update both when the change should apply site-wide.

    Arrange sections and media

    Choose an existing section

    Section Typical use
    Hero / Subject hero Page introduction and main call to action.
    Rich text Paragraphs, lists, headings and inline links; some pages support a split text/media layout.
    Card grid / Unique selling points Related topics, benefits and links.
    FAQs Questions and answers. Use the rich-answer field where available for formatted answers and links.
    Statistics / results, Results archive Approved achievement figures and year-by-year results.
    Pricing guide Fee rows, durations, effective/reviewed date, review notice and footnotes.
    Campus locations / Campus details Addresses, opening hours, contact information and location media.
    Call to action / Enquiry form Next-step links, quiz entry and website enquiries.
    Home-specific and subject-specific sections Existing designed compositions; edit their listed fields and item arrays.

    Available sections vary by page type. If a needed section is absent from the selector, ask Focusin Studio to confirm the intended page type or scope a new component.

    Background and spacing

    Open Section appearance. Background options are Design default, White, Soft grey, Light teal and Brand teal. Top/bottom spacing offers Design default, None, Compact, Standard and Spacious.

    Use the existing presets. For normal subject content, alternate Light teal and White so adjacent sections are distinct. Keep default/standard spacing unless the reviewed design calls for a change.

    Images and video

    • Upload or select the intended image, enter meaningful Alternative text, and check its crop on desktop and mobile. Avoid filenames as descriptions.
    • Where Mobile image (optional) is available, it is used below 768px; otherwise the desktop image is reused.
    • For video-capable sections, select Video, upload a Video file or supply a direct HTTPS MP4/WebM URL. A YouTube/Vimeo watch-page URL is not a direct video file. An uploaded file takes precedence over the URL.
    • Add a Video poster, Video description, and captions/transcript where available. Set Captions language to match the file, for example en or zh.
    • A Placeholder label is useful while approved media is pending. Replace it with approved media before final acceptance.
    • Check permissions for student photos, testimonials and results before publishing. Removing an image from one section does not mean its underlying asset is unused elsewhere.

    For buttons and navigation use root-relative site paths such as /contact-us; for external destinations use the full HTTPS address. Test both language versions after editing. Inline text links may need the explicit translated destination.

    Edit shared settings

    Publish the settings document after editing. A shared change can affect many pages at once.

    Site Settings

    Field Purpose
    Site Name Bilingual site name.
    Default SEO Title / Default SEO Description Global defaults when a page does not supply its own SEO wording.
    Subject banner — founder portrait One portrait used by subject heroes that enable the global founder image. Update its alternative text too.
    Google Analytics measurement ID GA4 ID beginning with G-. In this implementation it is managed in Sanity, not a Vercel variable. A valid ID enables the shared analytics integration.
    Contact Widget Show/hide the floating widget, bilingual labels, WeChat ID and QR code, WhatsApp link, and Calendly destination.

    Check the QR code with a phone after replacing it. Use a full WhatsApp link with country code. Calendly accepts an HTTPS booking URL or a site path such as /enrolment while a booking URL is unavailable.

    Header Settings

    Edit Phone, Announcement Text, Mobile Menu Title, Navigation Items, Desktop Courses Mega Menu, Primary CTA and Mobile Primary CTA Label.

    Drag Navigation Items to reorder them. Submenu Links produce grouped navigation. Use Courses mega menu for the Courses group; use Dropdown for other grouped items. Supply both language labels, a real destination and any needed description.

    To add a page to the menu: publish the page first → open Header Settings → add the item or child link → enter both labels and the root-relative path → publish Header Settings → check desktop and mobile menus in both languages.

    Footer Settings

    Edit Summary, Contact Email, Contact Phone, Contact Address, Social Links and Link Groups. Review other places displaying the same information, such as page sections, the header and contact widget; they are not all one shared field.

    Changing a displayed email address does not change where form submissions are delivered. The delivery inbox is configured separately in Vercel as CONTACT_TO_EMAIL.

    Welcome Quiz Settings

    Use Enable welcome quiz to control availability. Edit Quiz copy, parent/student year levels, subject labels and audiences, parent goals and student goal groups.

    Stable values connect quiz options and rules. Do not rename or delete a stable value without checking every reference. Changing a visible label is different from changing the underlying value. After editing, test both the parent and student paths in both languages, including conditional subjects and the final submission.

    Manage shared subject-page bottom sections

    Open Subject page bottom sections → English or 中文. This is independent of the homepage.

    1. Use Show global bottom sections to enable or hide the group for that language.
    2. In Sections, add an entry and give it an Editor label. This label is for editors, not visitors.
    3. Add exactly one Section content item: Teaching banner, CTA / quiz promotion, Contact details or Enquiry form.
    4. Use Show this section to hide an entry without deleting it. Drag entries to change the order.
    5. Publish and check representative subject pages in that language.

    These sections appear after local page content and before the footer. Editing one entry updates every subject page that inherits it. Do not copy shared sections into every page.

    Exceptions for a single page

    On the Subject Page, open Global bottom sections. Switch off Show global sections to hide the whole group, or use Hide selected sections for individual exclusions. Publish the page.

    Page-specific versions

    A shared entry can contain Page-specific versions. Add Page paths and exactly one Replacement section. Paths must be exact and root-relative, for example /mathematical-methods, without /zh, a trailing slash, query string or fragment. The setting already belongs to one language. Avoid duplicate/overlapping paths within the same entry.

    Renaming or reordering an entry preserves existing page exclusions. Deleting and recreating it produces a new entry, so review exclusions again. A missing language setting does not inherit the other language’s shared content.

    Publish blog posts

    1. Open Blog Post and create a document.
    2. Enter Title, Locale, Translation key and Slug. For a normal article, use a simple slug such as study-planning-tips, without blog/ or a language prefix.
    3. Add Excerpt (up to 220 characters), Category, Author, Published at, Main image, and the article Body.
    4. Complete SEO fields, review media permissions, and create the matching translation when needed.
    5. Preview and publish. Test the article at /blog/your-slug or /zh/blog/your-slug.

    Published at controls display/order; it is not a publication scheduler in this website. A future date does not keep an already-published article hidden. Leave an article as a draft until it should be available.

    To change the blog landing page, open the existing Blog Index for the correct language. Edit the headings, introduction, Posts per page (3–24), Featured post, final CTA and SEO fields. Publish the referenced article before publishing a featured-post selection, and choose the matching language.

    Preview, publish and verify

    Draft preview

    Ask Focusin Studio for a private preview link for the page you are reviewing. The current Studio configuration does not include a custom one-click preview panel. Preview access uses the website’s protected draft endpoint and requires administrator configuration.

    Open the link and confirm the visible preview banner. Check the page, then use Exit preview to return to the published version. Do not put secret-bearing preview links in this public guide or forward them widely.

    A Vercel preview deployment is not the same thing as Sanity draft preview: without draft mode, it normally reads published CMS content. Preview and production can also point at the same dataset; publishing to a shared dataset can affect both.

    Publish

    Resolve the document’s blocking validation errors, complete the content approval, then click Publish. Wait for confirmation and check the normal website outside draft mode. Each language document and each shared settings document is published separately.

    Content-only edits normally do not require a website code deployment. On the production website, the configured Sanity webhook refreshes the content cache. Reload an already-open page. If the webhook is unavailable, a five-minute cache fallback exists, but it is not a guaranteed five-minute update deadline.

    Before you finish

    • Check the page title, spelling, prices, dates and approved claims.
    • Open the page at desktop and mobile widths.
    • Test buttons, internal links, menus and the language switch.
    • Check pictures, video controls and captions.
    • For courses, test real program/year/campus combinations.
    • For shared settings, check more than one affected page.
    • Confirm the published version outside draft preview.

    Unpublish or remove content

    Use the document’s action menu for unpublishing where available. Coordinate removed URLs, links and redirects with Focusin Studio first. Some known pages have bundled fallback content in this implementation, so unpublishing alone is not a reliable way to guarantee that a public route disappears. Verify the actual website response. Do not delete shared assets or referenced documents without checking their usage.

    Forms, enquiries and registration

    The website’s Contact/Enrolment enquiry forms and Welcome Quiz send through the website backend and Resend. They are separate from the embedded external registration system.

    Change Where to make it
    Heading or introduction around a form The page’s Enquiry form section in Sanity.
    Visible contact email or phone Relevant page sections and shared Header/Footer Settings.
    Quiz wording and choices Welcome Quiz Settings.
    Inbox receiving website enquiries Vercel → CONTACT_TO_EMAIL.
    Email sender Vercel → CONTACT_FROM_EMAIL, using a domain verified in Resend.
    Email service credentials Vercel → RESEND_API_KEY, managed by the administrator.
    Embedded registration form fields and submissions The separate registration system; coordinate with its administrator.

    The Registration form section exposes its heading and introduction in Sanity. Its embedded destination, registration.bteducation.com.au, is defined in website code; it is not changed by editing the Contact enquiry form.

    After a delivery-setting change, send one agreed test enquiry and confirm it arrived in the intended inbox. A submission success message or provider acceptance is not proof of inbox receipt. Check spam and Resend delivery records if it is missing. Avoid including real student information in routine tests.

    SEO and safe content changes

    Set SEO title, SEO description and Social image on the page or post. The description field permits at most 180 characters. Use specific, readable descriptions instead of lists of keywords. A social image is separate from the hero image.

    Page content, global SEO defaults and GA4 ID live in Sanity. Canonical site origin, redirect rules, route behaviour, robots and sitemap generation involve website configuration/code. Ask the developer to coordinate domain or published-URL changes.

    Results, testimonials, pricing and student media require approved facts and permissions. Record outstanding items in review notes where available. Publishing a page should not be used as a substitute for resolving a factual uncertainty.

    Layer Technology Responsibility
    Website Next.js 16.3.1, React 19.2.8, TypeScript Pages, language routing, forms, search, SEO and server rendering.
    Styling Tailwind CSS 4 and shared components Responsive layouts, typography, colours and section presets.
    CMS Sanity Studio 6 and Sanity Content Lake Documents, media, drafts, publication and editor access.
    Hosting Vercel Builds, deployments, domains, environment variables and API routes.
    Email delivery Resend Website enquiry and quiz email transport.

    Give editors individual Sanity accounts. Project administrators manage member access in Sanity project management; Vercel and GitHub access are separate permissions. Routine editors should not need API tokens. Coordinate account ownership and access changes with the project owner.

    Administrator: Vercel variables

    Open the website’s Vercel project → Settings → Environment Variables. Select the intended environment: Production, Preview or Development. After a change, create a new deployment for that environment; existing deployments do not acquire the new value automatically. See Vercel’s environment-variable guide.

    This is a source-code inventory, not a readout of the values currently stored in Vercel. Actual credentials and inbox addresses must be obtained through the owner’s private handover.

    Variable Purpose and handling
    NEXT_PUBLIC_SITE_URL Public canonical website origin used for metadata and SEO URLs. Use the intended HTTPS origin; changing it does not switch DNS.
    NEXT_PUBLIC_SANITY_PROJECT_ID Public Sanity project identifier. Must point to the intended content project.
    NEXT_PUBLIC_SANITY_DATASET Content dataset. The code default is production; verify the actual environment before publishing.
    NEXT_PUBLIC_SANITY_API_VERSION Date-based Sanity API behaviour version. Code default: 2026-08-19. This is not the site’s content-update date.
    SANITY_API_READ_TOKEN Private server-side credential for draft preview and any content access that needs authentication. Keep it out of browser/public files.
    SANITY_PREVIEW_SECRET Private value protecting the draft-preview entry route. Share preview access privately.
    SANITY_REVALIDATE_SECRET Private value checked against the webhook’s x-sanity-webhook-secret header. Both sides must agree.
    RESEND_API_KEY Private credential for enquiry/quiz email delivery.
    CONTACT_FROM_EMAIL Sender, optionally with a display name, on a Resend-verified domain.
    CONTACT_TO_EMAIL One receiving address or a comma-separated list. Use agreed test recipients for testing and approved recipients for production.
    BT_NOVEMBER_ROUTES_RELEASED Developer-controlled release gate. The exact value true enables reviewed November route consolidation. Do not change it as an ordinary content edit.

    SANITY_API_WRITE_TOKEN appears in the environment example and is used by controlled content scripts. It is not required by the inspected public website runtime. Do not add a write token to Vercel merely because it appears in the template; the developer should decide where authorised maintenance scripts run.

    BT_NEXT_DIST_DIR changes the local/build output directory and is not a normal client setting. NODE_ENV and VERCEL_ENV are runtime/platform indicators; do not use them as editorial switches. Script-only values such as local preview ports are not ordinary production settings.

    Any name beginning with NEXT_PUBLIC_ is intended to be public. Never put a password, API secret or private token in one of those variables.

    November route gate

    The gate coordinates /vce-tutoring → /vce-program and /vce-tutoring/maths-methods → /mathematical-methods, including Chinese equivalents. The 11 November release record says it was still disabled then. Only the developer should enable it after checking the reviewed destination documents and deploying the matching code. This guide has not independently verified the current hosted value.

    Administrator: publishing and maintenance

    Content refresh webhook

    The administrator configures the Sanity webhook for the intended dataset and the website’s /api/revalidate endpoint. It uses POST for published-content changes, excluding drafts and release versions, with the custom header x-sanity-webhook-secret matching SANITY_REVALIDATE_SECRET in Vercel.

    The webhook’s separate signing-secret field is not a replacement for that custom header in this implementation. Check delivery logs: a successful request returns HTTP 200; HTTP 401 indicates a missing or mismatched configured secret. Confirm behaviour after changing domains or secrets.

    Different kinds of releases

    What changed? Required action
    Existing page text, images or settings Publish the relevant Sanity documents and verify the website.
    New schema fields or editor controls Developer updates and deploys Studio; renderer changes may also need a website deployment.
    Website behaviour, layout component or redirects Review, test and deploy the application through the configured Vercel workflow.
    Vercel environment variable Save for the right environment, redeploy and test the affected feature.
    Manual text Update and publish the static guide files to the separate Pages source.

    The GitHub repository contains quality checks, but confirm Vercel’s actual production branch and deployment settings in its dashboard before merging or releasing. An existing branch name is not proof of a production deployment target.

    Restore or correct a mistake

    For an incorrect edit, restore the approved wording in a new draft, or ask the administrator about document history available to the account; review and publish the correction. For a code incident, the developer can select a suitable Vercel deployment after checking compatibility with current content. A code rollback does not roll back Sanity content or environment configuration.

    Do not rerun old import/seed scripts as an editorial undo. Some maintenance scripts can overwrite reviewed content. Backups, imports, schema changes and dataset operations belong with the administrator.

    Troubleshooting

    Problem First checks
    I cannot sign in or edit Confirm your invited Sanity account, project and role with the owner. Do not share someone else’s login.
    The page is missing from a Studio category Search the general page-type list. Subject categories are filtered by URL prefix.
    Publish is blocked Open the validation messages and resolve the exact fields. Existing imported content can have validation issues; do not invent missing prices/dates to pass validation. Ask Focusin Studio where the intended correction is unclear.
    My change is saved but invisible Check document, locale, draft/publication status, website address and preview banner. Reload; then ask the administrator to inspect webhook delivery and content loading.
    An old page still appears after unpublishing Some known routes have bundled fallback content. Ask the developer to handle removal and redirects.
    A new page is not in the menu Add its destination in Header/Footer Settings or the relevant page card and publish that document too.
    A course is missing from the finder Check publication, locale, Show in course finder and a complete matching offering row.
    A language switch does not find the expected page Check the paired document’s type, Locale, exact Translation key and publication state.
    A change appeared on many subject pages Check shared bottom sections or the global founder portrait; use page exclusions for exceptions.
    A video does not play Check the selected media type, uploaded file or direct HTTPS video URL. Watch-page URLs are unsupported in this media field.
    An enquiry did not arrive Check the approved receiving inbox and spam, then Resend delivery records and the deployed email configuration.
    A button opens the quiz unexpectedly Check its Button action. Choose Open link when it should navigate normally.
    A changed URL shows a 404 or redirects Check the stored slug, publication state, language prefix and code-managed redirects/release gates.

    When reporting an issue, include the page URL, language, document title, field changed, approximate time, browser/device and expected versus actual result. A screenshot helps; exclude credentials and student enquiry details. Contact Focusin Studio at hello@focusin.com.au.
